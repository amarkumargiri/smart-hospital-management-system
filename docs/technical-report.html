Architecture

The path of one request

POST /api/consultations/{id}/complete   ← doctor clicks "Complete consultation"

  1  rate limiter        300 requests / minute / IP
  2  express.json        body parsed, capped at 1 MB
  3  authenticate        JWT verified → req.user = { id, role, doctorId, hospitalId, … }
  4  requireRole(DOCTOR) role gate
  5  handler             loads consultation, checks it belongs to this doctor,
                         refuses if no diagnosis recorded
  6  $transaction        consultation completed + appointment closed +
                         medical record written — all or nothing
  7  createConsultationBill()   idempotent, keyed on appointmentId
  8  notify()            row inserted for the patient
  9  audit()             failure here is logged, never breaks the request
 10  serialize()         Prisma Decimal → number, then JSON

Section 2

Technology stack

Sixteen packages — thirteen distinct libraries — and nothing else. Each one below states where it is used in this project, the use case that justified it, and what was considered and rejected. Anything the standard library or the platform could already do was not added.

Runtime and language

Node.js

v26, ES modulesRuntime
Where
The entire API process, the seed script, the forecasting engine and the test runner.
Use case
A hospital API is almost entirely I/O — database reads, writes and notification inserts. Node's event loop handles that concurrency without a thread per request.
Why
One language across API, forecasting and browser means one toolchain, one dependency file, one mental model. It also made it possible to put the forecasting models in the same process rather than in a second service.
Rejected
Java Spring Boot — the PRD's other suggestion. It would have forced the forecasting models into a separate Python service with a REST hop between them, adding a deploy unit, a failure mode and a serialisation boundary for no gain at this scale.

Express

4.22API framework
Where
src/index.js mounts 18 routers under /api; every route module is an express.Router().
Use case
Routing, middleware chaining and a single error surface. The middleware chain is exactly how the security model is expressed: authenticate, then role gate, then handler.
Why
The middleware model maps directly onto layered authorisation. One error handler at the bottom of index.js converts HttpError, Prisma constraint errors and Multer size errors into consistent JSON, so no handler repeats error formatting.
Rejected
Fastify (marginally faster, smaller ecosystem for this use), NestJS (decorators and modules add ceremony a 18-route API does not need).

Data layer

Prisma ORM

6.19Data access
Where
prisma/schema.prisma defines all 41 entities; src/db.js exports one client used by every route.
Use case
41 entities with deep relations — a patient history query pulls consultations, diagnoses, vitals, prescriptions, lab orders and admissions in one call through nested include. Hand-written SQL for that is a maintenance burden.
Why
Three specific properties earned it: the schema file is a single readable source of truth for the data model; $transaction makes the bed-allocation and discharge sequences atomic; and switching SQLite to PostgreSQL is a provider line plus an env var, because Prisma generates the dialect.
Rejected
Raw better-sqlite3 (fast, but 41 entities of hand-written joins), Sequelize/TypeORM (heavier, weaker relation ergonomics), Knex (query builder without a schema source of truth).

SQLite → PostgreSQL

dev → productionDatabase
Where
DATABASE_URL in server/.env, and the provider line in the schema.
Use case
Development, demonstration and evaluation need a database that works after npm install with nothing else running. Production needs concurrent writers and real backups.
Why
SQLite removes the single biggest setup obstacle — no server, no credentials, no container. The schema was deliberately written to avoid SQLite-only constructs so the move costs nothing: enum-like columns are String validated in src/constants.js, and the one JSON field (blood units by group) is stored as text. Both are portable.
Trade-off
SQLite serialises writers. Fine for a demo and a small clinic; PostgreSQL is the answer the moment two hospitals write concurrently at volume.

Security and validation

jsonwebtoken + bcryptjs

9.0 · 2.4Authentication
Where
src/lib/auth.js — password hashing, access-token signing, refresh-token rotation, OTP generation.
Use case
A stateless 30-minute access token keeps every request cheap to authorise, while a long-lived refresh token stored as a Session row keeps revocation possible.
Why this combination
Pure JWT cannot be revoked before expiry, which is unacceptable when a password changes. Pure server sessions cost a database read on every request. Pairing a short JWT with a revocable refresh row gets both: fast authorisation, and a password change that kills every live session immediately.
Detail
OTP codes use crypto.randomInt, never Math.random — a credential, however short-lived, must not come from a predictable generator. bcrypt runs at cost factor 10.

Zod

3.25Validation
Where
Every route: parse(schema, req.body) in src/lib/http.js wraps it so failures become a 400 with per-field messages.
Use case
The trust boundary. Clinical values need real bounds — temperature 25–45 °C, SpO₂ 30–100, systolic 40–300 — so a typo is rejected at the edge instead of being stored and later read as a vital sign.
Why
Schemas are values, so they compose: hospitalSchema.partial().omit({...}) derives the update schema from the create schema, and the two cannot drift apart. Coercion (z.coerce.number()) handles query strings without manual parsing.
Rejected
Joi (heavier, no type inference), express-validator (imperative chains scattered through handlers), hand-written checks (would have been the largest source of duplication in the codebase).

express-rate-limit

7.5Abuse control
Where
Globally at 300 requests/minute; tightened to 20 per 15 minutes on /api/auth/register, /login, /verify-otp and /resend-otp.
Use case
Credential endpoints are the obvious brute-force target, and a six-digit OTP is only strong if guesses are limited.
Why
Four lines of configuration for a real class of attack. In-memory storage is correct for a single instance; a Redis store is the documented upgrade when the API runs on more than one.

Multer

1.4.5-ltsFile upload
Where
src/routes/files.js — lab report scans, insurance documents, identity proofs, discharge summaries.
Use case
Multipart parsing with limits applied before anything touches disk: 15 MB, one file per request, and an allow-list of PDF, JPEG, PNG and WebP.
Why
Streams to disk instead of buffering whole files in memory. The client-supplied filename is discarded — the stored name is 16 random bytes plus an extension derived from the verified MIME type, which closes the path-traversal and double-extension routes in one step.

cors + dotenv

2.8 · 16.6Configuration
Where
src/index.js and server/.env.
Use case
In development the browser is on :5173 and the API on :4000. In production CORS_ORIGIN pins the single allowed origin.
Why
Secrets, database URL and OTP behaviour move between environments without a code change. .env.example is committed; .env is not.

Front end

React

18.3UI
Where
39 page components across three role apps, plus a shared component library in src/components/ui.jsx.
Use case
The screens are stateful and dense — a consultation page holds notes, vitals, diagnoses, a prescription builder, a test picker and the patient's history, all mutating independently.
Why
Component composition is what keeps 39 pages from being 39 duplicated fetch-loading-error blocks. One useApi hook and one <Async> wrapper carry loading, error and empty states everywhere, so a page describes only its happy path.
Rejected
Vue and Svelte are equally capable here; React was chosen for ecosystem depth and because it is the PRD's stated front end.

Vite

6.4Build tool
Where
Dev server on :5173 with a proxy for /api; production build to web/dist.
Use case
Sub-second cold start and instant hot reload while building 39 pages.
Why
The dev proxy is the quiet win: the browser always calls /api/... on its own origin, in every environment, so there is no environment-specific base URL and no CORS configuration to get wrong in development.
Rejected
Create React App (unmaintained, slow), Webpack (configuration cost for no benefit here).

React Router

6.28Routing
Where
src/App.jsx — three nested route trees under /app, /doctor and /reception.
Use case
Each role's routes live inside a <Require role=…> guard wrapping a shared <Layout>, so the role gate is declared once per area rather than per page.
Why
Nested layout routes match the shape of the problem exactly: one sidebar per role, many pages inside it. A user who lands somewhere they do not belong is redirected to their own home, not shown an error.

Recharts

2.15Charts
Where
Forecast chart with confidence band, occupancy trends, daily volume, revenue bars, department and payment-method pies, blood demand by group.
Use case
The forecast chart is the demanding one: historical actuals, predicted values and a shaded 95% interval on a single axis, with the two lines visually joined at the boundary.
Why
Composable React components (<ComposedChart> holding an <Area> plus two <Line>s) express that directly, and it renders responsively without manual sizing. Colours come from the same CSS variables as the rest of the interface, so charts follow the theme.
Rejected
Chart.js (imperative, canvas — awkward inside React), D3 directly (full control, far more code than these charts justify).

Plain CSS

one 8 KB fileStyling
Where
src/styles.css — custom properties, layout primitives, component classes.
Use case
A clinical interface with a small, consistent vocabulary: cards, tables, badges, stat tiles, a bed grid.
Why nothing was added
CSS custom properties give theming, and a prefers-color-scheme block gives a full dark theme in around forty lines. Tailwind would have added a build step, a configuration file and class-name noise in every component to replace a file that gzips to 2.4 KB.

Forecasting

Hand-written JavaScript models

no dependencyMachine learning
Where
src/forecast/models.js — moving average, seasonal naive, linear trend (ordinary least squares), Holt-Winters with additive trend and a seven-day season. metrics.js holds MAE, RMSE and MAPE.
Use case
Hospital demand series are short (one to three years of daily points) and dominated by a weekly cycle plus a slow trend and an annual season. Holt-Winters models exactly that shape.
Why not Python
The PRD suggested pandas, statsmodels and XGBoost. Those earn their place on wide feature matrices and long histories. Here the winning model is roughly seventy lines of arithmetic, and writing it in JavaScript removed an entire service: no second runtime, no REST hop, no serialisation boundary, no separate deployment. A full run — seven metrics × three horizons plus eight blood groups, 45 forecasts — completes in about 150 ms on two years of data.
Honest limit
If the hospital later wants exogenous features (weather, local events, epidemic signals) or gradient-boosted models, that is the point to add a Python service. The HospitalResourceDaily table is already the clean interface it would read from.

Three modelling decisions worth explaining

One bed table, not two The PRD lists Bed and ICUBed separately. They are modelled as one table with a type discriminator (GENERAL, ICU, ISOLATION, PRIVATE, EMERGENCY). A separate ICU table would duplicate every column, every status transition and every occupancy query, and allocating an ICU bed would need a second code path that could drift from the first.
Enum-like columns are strings SQLite has no enum type, so statuses are String with the permitted values listed in src/constants.js and enforced by Zod at the API boundary. This keeps the schema portable to PostgreSQL unchanged, and it puts the state machines — which appointment status may follow which, which lab status may follow which — in one readable file instead of scattered across handlers.
One daily row is the forecasting interface HospitalResourceDaily holds one row per hospital per day: OPD visits, admissions, discharges, occupied beds and ICU beds, theatre cases, oxygen, blood total and blood by group, revenue. Everything the models train on comes from that table and nothing else, which is why the engine can be tested against synthetic history and why a hospital can bulk-load its own past data without touching any other part of the system.

Section 4

Authentication workflows

Patient registration

Form submitted→ User + Patient created→ Status PENDING→ OTP issued→ Code verified→ ACTIVE + signed in
  1. Uniqueness check — email and mobile are checked together; a clash returns 409 before anything is written.POST /api/auth/register
  2. Create in one nested write — the User and its Patient profile are created in a single Prisma call, so a half-registered account cannot exist.
  3. Issue the OTP — six digits from crypto.randomInt, ten-minute expiry. In development it is logged and returned so the flow works without an SMS provider.
  4. Verify — the token is matched on user, purpose, code, unused and unexpired; consuming it marks it used so it cannot be replayed. The account becomes ACTIVE and a session is issued.POST /api/auth/verify-otp

Sign-in

  1. One endpoint, three roles — the credential check is identical for every role; only the destination differs. Separate endpoints per role would be three copies of one handler.POST /api/auth/login
  2. Identical failure message — a wrong password and an unknown account both answer "Invalid email/mobile or password." Distinguishing them tells an attacker which accounts exist.
  3. Branch on account state — blocked accounts are refused; unverified accounts get a fresh OTP and a 202; accounts with two-factor enabled get an MFA OTP and a 202.
  4. Issue the pair — a 30-minute access token, plus a 30-day refresh token stored as a revocable Session row with device and IP.

Token refresh — rotation

  1. Client hits a 401 — the API client in web/src/api.js catches it and refreshes silently, once.
  2. Old token is revoked, new one issued — rotation on every refresh means a stolen refresh token has a short useful life.POST /api/auth/refresh-token
  3. Original request is retried — the user never sees a login screen because a 30-minute token expired mid-session. Exactly one retry, so a genuine failure cannot loop.
Session control Patients can list their active sessions with device and IP and revoke any of them individually. Changing a password revokes all of them — the standard signal that old sessions should not survive.
Section 5

Appointment workflows

How a bookable slot comes to exist

  1. The doctor publishes windows — per weekday, for example Monday 09:00–13:00 and 17:00–20:00. The whole week is replaced in one transaction, so the schedule is never left half-updated.PUT /api/doctors/{id}/availability
  2. A date expands into slots — each window is walked in slotMinutes steps; a step that would overrun the window end is dropped.GET /api/doctors/{id}/slots?date=…
  3. Taken slots are removed — every appointment that day which is not cancelled or rejected removes its slot.
  4. Past slots are dropped — so today's list is genuinely bookable.

Booking

  1. Who is booking — a patient books only for themselves; reception may book for any patient at its hospital.POST /api/appointments
  2. Server-side slot validation — the requested time must fall inside a published window and land on a slot boundary. A hand-crafted request for 09:07 is refused even though the UI would never offer it.
  3. Create, or lose the race — the unique index on (doctorId, scheduledAt) decides. A collision surfaces as "This time slot is no longer available."
  4. Notify both sides — the doctor gets a new-request notification; the patient gets an awaiting-confirmation one.

Lifecycle — a state machine, not a free-form field

REQUESTED→ CONFIRMED→ CHECKED_IN→ IN_CONSULTATION→ COMPLETED
FromMay become
REQUESTEDCONFIRMED · CANCELLED · REJECTED
CONFIRMEDCHECKED_IN · CANCELLED · NO_SHOW
CHECKED_ININ_CONSULTATION · CANCELLED · NO_SHOW

terminal statesnothing

The table lives in src/constants.js and every transition is checked against it, so an appointment cannot jump from requested to completed. Patients may only move an appointment to cancelled; every other transition belongs to the clinic side.

The OPD queue

  1. Token at check-in, not at booking — A-01, A-02, … numbered per doctor per day, so the queue reflects who is physically present.
  2. Now serving — the appointment currently in consultation, or the last completed one.
  3. Estimated wait — patients ahead × the average measured consultation length for that doctor today, falling back to the doctor's configured slot length before any consultation has finished. A measured average beats a guessed constant.GET /api/appointments/queue/status
Section 6

Clinical workflows

Consultation

  1. Opening the screen starts it — creating the consultation and moving the appointment to IN_CONSULTATION happen together. Re-opening resumes rather than duplicating, because appointmentId is unique.POST /api/consultations
  2. Notes are saved incrementally — symptoms, clinical notes, treatment plan and follow-up date. A completed consultation is read-only.PUT /api/consultations/{id}
  3. Vitals are upserted and bounded — one vitals row per consultation. Every field has a plausible clinical range; out-of-range values are refused at the boundary. Reception may record vitals before the doctor sees the patient.PUT /api/consultations/{id}/vitals
  4. Diagnoses are appended — ICD-10 code, description, severity, primary flag. Multiple diagnoses per consultation are supported.POST /api/consultations/{id}/diagnoses
  5. Completion fans out — see the box below. Refused with "Record at least one diagnosis before completing the consultation." if none exists.POST /api/consultations/{id}/complete
One click, five effects, one transaction Completing a consultation marks it complete, closes the appointment and writes the MedicalRecord entry — all inside a single $transaction, so a partial completion is impossible. The consultation bill is then raised idempotently, the patient is notified that notes and prescription are available, and a follow-up reminder is created if a date was set.

Prescription

  1. Access is re-checked — the doctor must have a treating relationship with the patient, independently of the consultation screen.POST /api/prescriptions
  2. Items carry full dosing — medicine, dose, frequency, duration in days, route (oral, IV, IM, topical, inhaled) and instruction.
  3. A record entry is written — so the prescription appears in the patient's timeline, not only under the prescriptions tab.
  4. Audited and notified — CREATE_PRESCRIPTION goes to the audit log; the patient is notified.
  5. Cancellation is narrow — only the prescribing doctor, and only while nothing has been dispensed against it.
Section 7

Laboratory workflow

Doctor ORDERED→ Reception SAMPLE_COLLECTED→ PROCESSING→ RESULT_ENTERED→ 2nd account VERIFIED
  1. Order — the doctor picks tests from the hospital catalogue and a priority: routine, urgent or STAT.POST /api/lab/orders
  2. Queue order — STAT first, then urgent, then routine; oldest first inside each band.
  3. Collect — a sample identifier is assigned; collection time and collector are stamped automatically.POST /api/lab/orders/{id}/collect
  4. Process — visible to the ordering doctor as progress.
  5. Enter results — value, unit, reference range and flag per test. A result naming a test that is not on the order is rejected. The order advances as a whole, so a half-filled report never reaches the patient.POST /api/lab/orders/{id}/results
  6. Verify and release — the gate described below.POST /api/lab/orders/{id}/verify
The four-eyes gate The account that entered the results cannot release them — "Results must be verified by someone other than the technician who entered them." This is a patient-safety property, not paperwork, and it survived the reduction to three roles: it is the reason the seed creates two reception accounts rather than one.
What verification triggers, in one transaction The report is marked verified with the verifier and timestamp, the order moves to VERIFIED, and a MedicalRecord entry is written — typed as imaging or laboratory according to the tests ordered. Then the patient is notified that the report is ready, and the ordering doctor is notified with the values, escalated to CRITICAL severity if any result carries a critical flag. The release is written to the audit log.

Until verification the patient sees the order as in progress, never as a result. A patient requesting an unverified report directly is refused.

Section 8

Pharmacy workflow

Stock

  1. Receive — medicine, generic name, form, strength, batch, quantity, reorder level, expiry, supplier, price. Stock already past its expiry date is refused on entry.POST /api/pharmacy/inventory
  2. Restock is an upsert — the same medicine and batch increments that batch rather than creating a second row, so batch quantities stay meaningful.
  3. Three standing alert lists — expired, expiring within thirty days, and at or below the reorder level.GET /api/pharmacy/alerts

Dispensing

  1. Queue — active prescriptions written by this hospital's doctors, newest first.GET /api/pharmacy/prescriptions
  2. Every line is validated before anything changes — the batch must exist, belong to this hospital, be unexpired, hold enough units, and the prescription line must belong to that prescription. All checks run before the first write.
  3. Dispense atomically — stock decrement, dispensed quantity on the prescription line, and a DispenseRecord for the audit trail — one transaction per item, all in one call.POST /api/pharmacy/dispense
  4. Reorder alerts fire immediately — anything that crossed its reorder level during this dispense notifies the reception desk with the remaining quantity.
Why oxygen and blood are inventory items Oxygen cylinders and blood units are stocked like any other medicine, so their consumption flows into the same daily snapshot the forecasting engine trains on. Blood carries its group in the strength field, which is what makes a per-group demand forecast possible without a separate blood-bank subsystem.
Section 9

Inpatient workflows

Admission

Doctor REQUESTED→ Reception APPROVED→ ADMITTED→ Doctor DISCHARGED or REJECTED
  1. Doctor requests — reason and working diagnosis. Refused if the patient already has an open admission, which prevents duplicate stays.POST /api/admissions
  2. Reception approves or rejects — a rejection notifies the requesting doctor.
  3. Bed allocation admits the patient — claiming the bed and admitting are the same transaction; see Section 14.POST /api/admissions/{id}/admit
  4. Transfer — the new bed is claimed and the old released to cleaning together, so no interval exists where the patient occupies two beds or none.POST /api/admissions/{id}/transfer

Bed states

AVAILABLE→ OCCUPIED→ CLEANING→ AVAILABLE also RESERVED MAINTENANCE

A discharged bed goes to CLEANING, never straight to available — it is not usable until turned over. An occupied bed cannot be edited directly: "Discharge the patient before changing this bed status." Hospital bed and ICU capacity are derived from the bed table itself, so the public profile and the forecast denominators are never typed in twice.

Surgery scheduling

  1. Book a theatre — theatre, surgeon, optional admission, procedure, start time, duration and charge.POST /api/ot/surgeries
  2. Overlap is rejected — candidate bookings are narrowed by the longest allowed duration, then the exact overlap test runs in JavaScript, because a relational WHERE cannot express "start + duration > x".
  3. The theatre follows the surgery — in use while operating, cleaning when complete, available if cancelled.

Discharge

  1. Write the summary — final diagnosis, procedures, medications, investigation summary, instructions, follow-up date and discharge type (routine, against medical advice, referred, death).POST /api/admissions/{id}/discharge
  2. Four writes, one transaction — the discharge record, the admission status, the bed released to cleaning, and a MedicalRecord entry.
  3. Consolidated bill — room or ICU nights (part-days round up, minimum one), verified lab and imaging, completed surgeries, and medicines dispensed during the stay.
  4. Patient notified — with the final bill number and total; the summary becomes downloadable.
Section 10

Emergency workflow

  1. Register without an account — a walk-in needs only a name and optionally a phone. Requiring an unconscious patient to sign up first is not a workable triage flow, so the case can exist before the patient record does.POST /api/emergency
  2. Triage — critical, high, medium or low. The working queue sorts by triage first and arrival time second, and re-triage is one dropdown.
  3. Assign a doctor — the assigned doctor is notified immediately, at CRITICAL severity when the triage level is critical.
  4. Allocate an emergency bed — the same atomic claim as a ward admission; the previous bed, if any, is released to cleaning.POST /api/emergency/{id}/allocate-bed
  5. Escalate to an admission — creates an approved admission and closes the emergency case. This requires a registered patient, so a walk-in must be registered first — the one place the shortcut has to end.POST /api/emergency/{id}/admit
Section 11

Billing workflows

Where bills come from

TriggerBill produced
Consultation completedConsultation fee. Idempotent through the unique appointmentId — a retry returns the existing bill.
Patient dischargedConsolidated stay: room or ICU nights, verified lab and imaging, completed surgeries, medicines dispensed during the stay.
Reception creates oneManual bill for walk-in services, with any line items.
The total is never stored independently of its items Every mutation — adding an item, removing one, applying a discount or tax, recording a payment — routes through one recalculate() function that re-derives subtotal, total, paid amount and status from the line items and payments. A bill total can therefore never disagree with what the bill is made of, which is the failure mode that makes billing bugs expensive.

Payment

  1. Who may pay — the patient for their own bill, or reception for any bill at its hospital.POST /api/billing/{id}/payments
  2. Overpayment refused — "Payment exceeds the outstanding amount of N."
  3. Status derives itself — pending, partially paid or paid, computed from payments rather than set by hand.
  4. Patient notified — with the amount recorded and the balance remaining.

Insurance

  1. Policy on file — provider, policy number, coverage amount, validity, optional document.POST /api/billing/insurance
  2. Claim raised against a bill — the policy must belong to that patient and the claim cannot exceed the bill total.POST /api/billing/{id}/claims
  3. Settlement becomes a payment — recording a settled claim with an approved amount automatically writes an INSURANCE payment for that amount. Money received is money recorded — the two cannot drift apart.PUT /api/billing/claims/{id}
Money is Decimal, never Float All monetary columns use Prisma's Decimal. Because Decimal serialises to a string by default, a serialize() helper converts it to a number on the way out, so the client never receives "900" where it expects 900.
Section 12

Forecasting pipeline

The feature that separates this from a booking system: it converts operational history into 7, 14 and 30-day predictions of demand, and warns before capacity is breached rather than after.

Step 1 — the daily snapshot

captureDailySnapshot() rolls one day of live activity into a single HospitalResourceDaily row: OPD visits, admissions, discharges, occupied beds and ICU beds, theatre cases, oxygen dispensed, blood units total and by group, and revenue collected. It upserts on (hospitalId, date), so re-running it corrects the row rather than duplicating it. Hospitals migrating historical data use the bulk ingest endpoint instead.

Step 2 — the data quality gate

RuleSeverityEffect
Invalid or future dateERRORRow excluded
Duplicate dateERRORRow excluded
Negative quantityERRORRow excluded
Occupancy above capacityERRORRow excluded — the two figures came from different places
Missing valueWARNINGRecorded, row kept
Outlier beyond 4σWARNINGFlagged but kept
Why outliers are kept A four-sigma spike in OPD visits is usually a real surge — an epidemic week, a mass-casualty event — and that is exactly the pattern management needs the model to have seen. Rows are only excluded when they are internally impossible, such as more occupied beds than beds.

Step 3 — the model race

ModelCapturesRole
Moving averageLevel onlyBaseline — proves the others earn their place
Seasonal naiveWeekly cycleStrong on stable weekday patterns
Linear trend (OLS)DirectionWins on smoothly drifting series such as ICU occupancy
Holt-WintersLevel + trend + 7-day seasonUsually wins; smoothing constants grid-searched over 125 combinations

All four predict a held-out window of recent history. The lowest MAPE wins, is refit on the full series, and produces the real forecast. Zero actuals are skipped when computing MAPE rather than counted as infinite error. The confidence band is ±1.96 × the residual spread of the winning model, clamped to the metric's valid range — an occupancy forecast can never print 104%.

Different metrics select different winners, which is the point of racing them. The dashboard prints the winning model and its error rate beside every number, so a forecast is never presented as more certain than it is.

Step 4 — alerts

MetricConditionSeverity

Alerts are derived from the forecast, not from live occupancy, which is what makes them actionable — the warning arrives days before the ceiling is reached. Each carries a recommended action, notifies the reception desk, and is acknowledged once handled. Alerts fire on the shortest horizon that crosses a threshold, so one capacity risk does not produce three near-identical warnings.

Where the training data comes from

The seed generates two years of synthetic daily history from a deterministic pseudo-random generator, so every run produces identical data and comparable accuracy numbers. It layers a weekday factor (Sunday quiet, Monday heavy), an annual respiratory season peaking in January, a slow growth trend, a festival dip, and Box-Muller Gaussian noise. Occupancy carries over day to day, driven by the admission and discharge balance and pulled back toward a comfortable level; oxygen tracks ICU load; blood tracks theatre cases and admissions. The result is a series with genuine structure for the models to find, rather than noise they cannot beat.

Section 14

Concurrency and integrity

Four places where two users can collide. Each is handled at the database, not with an application-level check that a second request can slip past.

1 · Two patients, one appointment slot

@@unique([doctorId, scheduledAt])        // schema.prisma

try { await prisma.appointment.create({ … }) }
catch (err) {
  if (err.code === 'P2002')
    throw conflict('This time slot is no longer available. Please select another slot.')
  throw err
}

Checking availability and then inserting leaves a window between the two. The unique index closes it: the database rejects the second insert whatever the timing, and the handler translates that into a message the patient can act on.

2 · Two patients, one bed

const claimed = await tx.bed.updateMany({
  where: { id: bedId, hospitalId, status: 'AVAILABLE' },   // ← the guard
  data:  { status: 'OCCUPIED' },
})
if (claimed.count === 0) return null                        // someone else won

A conditional update is an atomic compare-and-set: the bed is claimed only if it is still available at that instant. The count tells the handler whether it won. Because the claim and the admission are in the same $transaction, a bed can never be marked occupied without a patient in it. The same pattern protects transfers and emergency bed allocation.

3 · A bill paid twice

Every payment triggers recalculate(), which re-derives the paid amount from the payment rows themselves rather than incrementing a counter. Two concurrent payments therefore both land and the total is correct; a payment exceeding the outstanding balance is refused outright.

4 · A duplicate bill from a retried request

Consultation billing is keyed on the unique appointmentId. If the request is retried — a flaky connection, an impatient click — the function finds the existing bill and returns it. The same idempotence protects the discharge bill through its admission link.

Section 15

Security model

Three layers, in order

  1. Authentication — authenticate verifies the JWT and loads the user with their patient, doctor or staff profile, so req.user carries patientId, doctorId and hospitalId and no handler re-queries them. A blocked account is refused here.
  2. Role — requireRole(...) gates the route. There is no bypass account: the platform-wide role does not exist.
  3. Relationship — assertPatientAccess() is the layer that matters clinically, described below.
PRD section 52, implemented literally A doctor does not automatically see every patient. src/lib/access.js grants access only where an appointment, consultation, admission, lab order or prescription links that doctor to that patient. Reception sees patients with a record at its own hospital. A patient sees only themselves. Every other case is refused with "You do not have permission to access this record."

What the unit tests actually assert

  • MAE, RMSE and MAPE return their textbook values on a worked example.
  • MAPE skips zero actuals instead of returning infinity.
  • Seasonal naive reproduces a known weekly pattern to within 2% error.
  • Holt-Winters beats a flat moving average on a seasonal series — the complex model must earn its place, not merely run.
  • Linear trend extrapolates a straight line exactly.
  • Holt-Winters refuses a series shorter than two seasons rather than fitting nonsense.
  • Negative quantities, duplicate dates, future dates and occupancy-above-capacity are excluded.
  • A genuine surge is flagged as an outlier but kept in the training set.
  • ICU, bed, oxygen and blood alerts fire at their thresholds and stay silent below them.

Guards proven live by the end-to-end run

  • Double-booking the same slot returns 409.
  • Booking off a slot boundary returns 400.
  • Verifying one's own lab results is refused.
  • Overpaying a bill is refused.
  • One patient cannot read another patient's history.
  • A doctor is refused pharmacy, beds, analytics and forecasting endpoints.
Deterministic by design The seed uses a fixed-seed Mulberry32 generator, so every run produces identical demo data and therefore comparable forecast accuracy between runs. A change in MAPE means the model changed, not the dice.

Deliberate simplifications

Corners cut on purpose. Each is listed with the ceiling it hits and the upgrade that removes it, so none of them becomes a surprise later.

SimplificationCeilingUpgrade path

What is not simplified

Input validation at the trust boundary, error handling that would otherwise lose clinical data, every security measure, and the transactional guarantees around beds, billing and consultations. Those are where a shortcut costs more than it saves, and none was taken.
